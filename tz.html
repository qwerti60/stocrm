1. Цель

Дать клиентам автосервиса своё приложение (как у FIT SERVICE): записаться на пост без звонка, видеть свои авто и историю работ, отслеживать текущий ремонт. Все заявки, контакты, автомобили и заказ-наряды живут в уже используемой STOCRM — приложение не дублирует учёт, а является клиентским каналом к CRM.

Не путать со штатным приложением STOCRM (для сотрудников) и GoodGarage (универсальное клиентское приложение вендора). Здесь — ваше брендированное приложение в сторах, со своим логотипом, картой филиалов и сценариями в духе FIT SERVICE.

4. Функциональные требования (этап 1)

4.1. Вход

  1. Экран телефона РФ (+7), отправка OTP по SMS.
  2. После кода — сессия (JWT). Повторный вход без повторной регистрации, если номер уже есть.
  3. Поиск/создание контакта в STOCRM по телефону. Источник сделки: Онлайн-запись (в API — SOURCE_ID, у вендора встречается код 10049; фактический ID источника согласуем в кабинете заказчика).

4.2. Главная

  • Активное авто из гаража, пробег, дата следующего ТО (если известна).
  • CTA «Записаться».
  • Ближайшая запись (дата, филиал, услуга, статус).
  • Быстрые действия: шиномонтаж, ТО, диагностика, кузов (набор согласуем).
  • Блок акций (1–3 карточки).

4.3. Гараж

  • Список автомобилей клиента.
  • Добавление: госномер, марка/модель, год, VIN (необяз.), пробег.
  • Синхронизация с карточкой авто в STOCRM, если API отдаёт транспорт контакта. Иначе храним у себя и привязываем к сделке комментарием / кастомным полем.

4.4. Онлайн-запись

  1. Выбор авто → услуги (из справочника, согласованного с каталогом работ STOCRM) → филиала.
  2. Дата и время. Слоты: на этапе 1 — рабочие окна филиала (график) без жёсткой блокировки поста, заявка уходит как сделка. На этапе 2 — запись в календарь постов STOCRM, если вендор откроет нужные методы.
  3. Комментарий клиента («стук в подвеске», «замена масла 5W-40»).
  4. Создание сделки: POST /offer/new/with_contact (телефон, имя, комментарий, филиал, источник «Онлайн-запись»).
  5. Клиенту — подтверждение в приложении; приёмщику — сделка в воронке STOCRM.
  6. Отмена заявки клиентом до статуса «принят на пост» (правило: не позднее чем за N часов, N задаёт заказчик).

4.5. Филиалы

  • Список точек: адрес, телефон, график, услуги, координаты.
  • Карта (Yandex / OSM). Маршрут — системным навигатором.

4.6. История и записи

  • Предстоящие и прошлые визиты.
  • Карточка: работы, запчасти, сумма, дата — по данным сделки/ЗН из STOCRM, насколько отдаёт API.

4.7. Профиль

  • Имя, телефон, согласие на пуши и рассылки (152-ФЗ).
  • Политика ПДн, оферта, «о приложении».

5. Интеграция STOCRM

Ключ SID не кладём в приложение. Мобильный клиент ходит только на наш Backend-for-Frontend (BFF). BFF хранит SID, домен STOCRM и ходит во внешний API.

5.2. Ограничения API (важно)

Публичная wiki STOCRM хорошо покрывает сделки и склад. Календарь постов, список авто контакта, статусы ЗН «для клиента» могут требовать дополнительных методов — их выдаёт персональный менеджер STOCRM по SID. На старте работ:

  1. Заказчик даёт SID, домен аккаунта, тестовый контакт.
  2. Исполнитель снимает карту доступных методов (1–2 дня).
  3. Если календарь API недоступен — этап 1 работает через сделки-заявки; слоты постов — этап 2 после открытия методов или webhook.

5.3. Идентификация клиента

Канонический ключ — телефон. BFF хранит contact_id STOCRM после первого успешного создания/поиска. Повторные записи идут в существующий контакт, без дублей (дедуп по нормализованному +7XXXXXXXXXX).

6. Архитектура

Клиент: Flutter 3.x, одно приложение → iOS и Android (сборка в RuStore — по запросу).

BFF: FastAPI или Node (Nest), PostgreSQL: пользователи, сессии, кэш справочников, журнал заявок (id сделки STOCRM), контент акций.

Интеграции: STOCRM External API; SMS OTP (SMS.ru / SMSC / аналог РФ); push — FCM (+ APNs через FlutterFire). ЮKassa, чат, лояльность — этап 2.

Хостинг BFF: VPS РФ (Timeweb / Selectel). Логи без полных PAN/OTP.

6.1. Поток записи

  1. Клиент подтверждает слот в приложении.
  2. BFF пишет заявку в свою БД (статус pending).
  3. BFF вызывает STOCRM offer/new/with_contact.
  4. Ответ CRM: OFFER_ID сохраняется. Статус sent.
  5. Ошибка CRM — заявка failed, алерт в Telegram администратору, клиенту — «перезвоним».
  6. Опционально webhook/poller: статус сделки в CRM → статус в приложении.

7. Нефункциональные требования

  • Язык интерфейса: русский.
  • Первый запуск до главного экрана < 3 с на среднем Android (без холодного Flutter web).
  • Офлайн: кэш гаража и последней записи; запись без сети — очередь на отправку.
  • 152-ФЗ: согласие при OTP, политика на экране, хранение ПДн в РФ.
  • SID, SMS-ключи — только в секретах сервера.

9. Этап 2 (вне MVP, в пакете «как FIT»)

  • Живой статус ЗН и push «авто готово».
  • Рекомендации из заказ-наряда и напоминание ТО.
  • Бонусный баланс (простое начисление % от работ или связка с модулем лояльности STOCRM, если есть).
  • Чат: виджет в приложении, сообщения в Telegram/MAX администратора или Wazzup.
  • Онлайн-оплата предоплаты / ЗН (ЮKassa) — отдельная оценка, если нужны кассовые чеки.
  • Запись строго в календарь постов STOCRM.

10. Не входит

  • Замена STOCRM, склад для кладовщика, зарплата механиков.
  • Приложение для сотрудников (у STOCRM своё).
  • ОСАГО-калькулятор, партнёрский маркетплейс АЗС — как у федерального FIT.
  • Продление аккаунтов Apple / Google со 2-го года (тариф на тот момент неизвестен).
  • Доработки самой STOCRM со стороны вендора (ждём их API).

11. Нужно от заказчика

  • Домен STOCRM и SID (через менеджера STOCRM).
  • Список филиалов, график, координаты, телефоны.
  • Справочник услуг для записи (10–30 позиций на старт).
  • Логотип, цвета, название приложения в сторах.
  • Правило отмены записи (N часов).
  • Реквизиты ИП/ООО и документы для регистрации Apple Developer и Google Play (аккаунты оформляем в пакете сторов).
  • Юридические тексты: политика ПДн, согласие на рассылку.

12. Приёмка MVP

  • Сборка iOS (TestFlight) и Android (APK/AAB).
  • OTP на реальном номере.
  • Тестовая запись создаёт сделку в STOCRM заказчика с источником «Онлайн-запись».
  • Гараж сохраняется, история подтягивается или отображается из журнала BFF, если CRM не отдаёт ЗН.
  • Филиалы и акции редактируются без релиза приложения (контент на BFF).

ТЗ v1.0 — рамка для сметы и прототипа. Карта методов STOCRM уточняется после выдачи SID. Изменения состава экранов — доп. соглашение.
